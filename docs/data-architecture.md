# Data Architecture

## Purpose

`marklee.au` is a visual data portfolio. The default architecture should keep data processing separate from browser rendering and keep the client payload small enough for mobile devices.

## Default flow

The current repository uses static Astro output in `dist/`, with no Cloudflare adapter, Wrangler configuration or resource bindings. Preserve the working Worker deployment described in [deployment workflow](deployment-workflow.md). Data preparation remains separate from `npm run dev` and `npm run build`; neither command fetches source datasets or changes production data.

```text
PUBLIC SOURCE
     |
     v
 data/raw/
     |
     v
 processing script
 Python / TypeScript
     |
     v
 data/processed/
     |
     v
 browser-ready export
     |
     v
 public/data/<project-slug>/
     |
     v
 Astro / D3 / MapLibre visualisation
```

The source and processing stages can evolve per project, but browser assets should remain a deliberate final output rather than a copy of the raw source.

## Repository directories

### `data/raw/`

Use for downloaded or captured source datasets.

Rules:

- Local working data by default.
- Add to `.gitignore` by default.
- Keep a small sample only when it materially helps tests or reproducibility.
- Only `README.md` is tracked by default; any fixture needs a deliberate ignore exception and documented reuse terms.
- Never expose directly through the website.
- Do not place private employer data here.

### `data/processed/`

Use for intermediate analytical outputs.

Rules:

- Generated by scripts where practical.
- Usually ignored by Git when outputs are large or reproducible.
- In this repository all contents except `README.md` are ignored by default.
- Small stable fixtures may be committed when they support testing.
- Not directly exposed to visitors.

### `data/sources/`

Use for source notes and provenance records.

Each project should record:

- source name
- source URL or API endpoint
- publisher
- licence or reuse terms
- retrieval method
- retrieval date
- source update frequency
- geographic coverage
- date coverage
- field definitions when needed
- caveats and known quality issues

### `public/data/<project-slug>/`

Use only for browser-ready public assets.

Examples:

```text
public/data/pulse-of-adelaide/
  stations.json
  timeline.json
  summary.json
  metadata.json
```

These are proposed filenames, not existing fuel data. No fuel source has been established; see [Plan 002](exec-plans/active/002-pulse-of-adelaide.md).

Rules:

- Every file anywhere under `public/` is public, including READMEs and non-data assets. Gitignore does not prevent deployment of files placed there.
- Keep only fields required by the visualisation.
- Prefer compact JSON, GeoJSON, CSV, or prebuilt binary formats supported by the chosen client library.
- Split data by time, geography, zoom, or feature when that lowers initial load cost.
- Avoid duplicating the same large data in multiple files.

### `scripts/data/`

Use for reusable ingestion, cleaning, validation, and export scripts.

Use `scripts/data/<project-slug>/` for project-specific pipelines. Add scripts and schema-specific validation when a real dataset establishes the requirements; do not add dependencies to validate empty folders.

## Static assets are the default

For early DATA, MAPS, and LAB projects, prefer browser-ready assets deployed with the Worker.

Typical fetch:

```js
fetch('/data/pulse-of-adelaide/stations.json')
```

The same relative path should work in local development and on `marklee.au`.

Astro copies `public/data/` to `dist/data/` as part of the existing static build. Deploy through the existing Cloudflare setup; this plan does not configure or replace its asset handling.

## Storage decision order

Use the simplest storage option that satisfies the project.

Before adding D1, R2 or KV, record actual derived payload sizes, initial transfer and loading/query needs, update frequency and why static exports or chunking are insufficient. Document the chosen service, local isolation and production access in the project's execution plan before implementation. These are conditional options, not an infrastructure roadmap.

### 1. Static assets

Use when:

- the data is public
- updates are tied to deployments or scheduled preprocessing
- the browser can load the derived dataset efficiently
- server-side querying is unnecessary

Default choice.

### 2. D1

Use when:

- data is relational or tabular
- the browser should query subsets rather than download the full history
- filters or date ranges are better handled server-side
- the dataset updates independently of a site deployment
- an API endpoint needs SQL-backed responses

Do not add D1 only because a dataset is tabular.

No D1 tooling or bindings are currently installed or configured.

### 3. R2

Use when:

- files are too large or numerous to treat comfortably as normal deployed assets
- the project needs archives, large GeoJSON, Parquet, map tiles, imagery, or downloadable source packages
- independent object lifecycle is useful

Do not use R2 for small JSON files that fit naturally in static assets.

### 4. KV

Use for small, read-heavy values such as:

- latest snapshot metadata
- cached API results
- dataset version identifiers
- last successful ingestion timestamp
- small configuration values

Do not use KV as the canonical historical analytical store.

## Local and production parity

Static assets should work with the normal local development command used by the Astro project.

Run `npm run dev` for development and `npm run build` followed by `npm run preview` for the production output. These commands currently have no Cloudflare storage access.

If D1, R2 or KV is introduced, document and verify isolated local resources with the tooling chosen at that time. Do not assume a binding is local without checking its configuration. Production-mutating remote commands or bindings require an explicit task requirement and user approval. Do not add them to default development, build, preview or validation commands.

## Browser performance budget

Treat these as planning targets, not hard platform limits:

- Prefer an initial visualisation data transfer below about 2 MB compressed.
- Avoid forcing a mobile browser to download a full dataset when the first view needs only a subset.
- Consider chunking when total browser data approaches 10 MB or interactions do not need all records at once.
- Precompute statistics, indexes, coordinates, categories, and animation states when doing so materially reduces browser work.
- Prefer progressive loading for large maps and long timelines.

Codex should profile actual payload sizes before adding infrastructure solely because a raw source file is large.

## API keys and external APIs

Never place secret API keys in client JavaScript or `public/`.

If a project needs a secret-backed external API:

1. prefer an explicit local or scheduled preprocessing step that exports a permitted public snapshot
2. keep credentials in ignored local environment configuration or the chosen job's secret store
3. export only fields whose redistribution is permitted
4. add a Worker API only if the project contract establishes a runtime requirement; keep secrets server-side and return/cache only permitted fields

## Generated data

Generated browser datasets should be reproducible where practical.

Prefer:

```text
source data + processing script -> browser asset
```

over manually edited JSON.

Generated files should carry metadata that lets a future reader determine when and how the data was produced.
